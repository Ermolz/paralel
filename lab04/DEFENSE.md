## 1 Идея работы и устройство MPI

### Отдельные процессы и обмен сообщениями

MPI — интерфейс передачи сообщений. OpenMPI — реализация этого интерфейса, а пакет `mpi` даёт нашей Java-программе доступ к ней. `mpirun` запускает несколько экземпляров программы. Каждый выполняет свой `main`, работает в своей JVM и имеет собственные массивы. Одинаковое имя `data` в двух процессах не означает общую область памяти.

После `MPI.Init(args)` процесс узнаёт свой номер через `getRank()` и число участников через `getSize()`. Ранг — номер внутри конкретного коммуникатора. MPI-процессы могут исполняться на одном компьютере или разных компьютерах. Их число не является числом физических ядер.

Коммуникатор задаёт участников обмена, порядок их рангов и отдельный контекст сообщений. В `MPI.COMM_WORLD` находятся все процессы данного MPI-запуска. Другой коммуникатор может объединять только часть из них. Даже одинаковые теги в разных коммуникаторах не смешивают сообщения этих коммуникаторов.

Чтобы `recv` получил нужную отправку, должны согласоваться коммуникатор, отправитель, получатель и тег. Тег — целочисленная метка сообщения, выбранная программой. Тип данных и количество элементов описывают содержимое. Например, `count=5` вместе с `MPI.INT` означает пять целых чисел, а не пять байтов. В наших примерах отправитель и получатель используют согласованные типы.

### Проверить сообщение и принять сообщение

Иногда размер массива заранее неизвестен. Приёмник не может сразу выделить массив правильной длины, поэтому сначала запрашивает сведения о сообщении.

`probe(source, tag)` блокирует вызывающий процесс, пока подходящее сообщение не станет доступно для приёма, и возвращает `Status`. Само сообщение этот вызов не забирает. После него всё равно нужен `recv`. Успешный `probe` также не означает, что пользовательский массив получателя уже заполнен.

Из `Status` можно получить:

| Вызов | Смысл |
| --- | --- |
| `getSource()` | Ранг отправителя в данном коммуникаторе. |
| `getTag()` | Тег найденного сообщения. |
| `getCount(MPI.INT)` | Число элементов сообщения при интерпретации его согласованным типом `MPI.INT`. |

`iProbe(source, tag)` проверяет наличие сообщения без ожидания. В используемых Java bindings результатом будет `null`, если подходящего сообщения пока нет, и объект `Status`, если оно есть. Это позволяет между проверками делать другую работу. Цикл, который непрерывно вызывает `iProbe`, сам по себе полезных вычислений не выполняет: это опрос состояния.

### Блокирующий вызов и момент завершения

Блокирующий `send` возвращает управление, когда отправляющий буфер можно безопасно использовать снова. Из этого не следует, что получатель уже обработал данные или даже вернулся из своего `recv`. Для небольших сообщений MPI может скопировать данные во внутренний буфер и завершить `send` до входа получателя в приём.

Внутреннее буферизованное поведение часто называют eager-протоколом. Для более крупных сообщений реализация может требовать согласования с приёмником, то есть использовать rendezvous-подобный обмен. Конкретные алгоритмы и границы зависят от реализации, транспорта и настроек. Рассчитывать на фиксированную границу размера или обязательную буферизацию нельзя.

Блокирующий `recv` возвращает управление после завершения приёма в указанный буфер. После этого данные в нём можно читать. Таким образом, слово «блокирующий» относится к условиям возвращения из вызова у данного процесса, а не к одновременной остановке всей программы.

### Асинхронный запрос и прямой буфер

`iSend` и `iRecv` запускают операцию и возвращают `Request`. Запрос представляет незавершённую операцию. Префикс `i` не означает создание отдельного Java-потока для каждой отправки и не гарантирует, что вся передача уже закончена к возврату из вызова.

`request.waitFor()` ждёт завершения именно связанной с этим запросом операции. Для отправки завершение разрешает повторно использовать отправляющий буфер, для приёма — читать полученные данные. До завершения отправки содержимое передаваемой области менять нельзя; до завершения приёма результат читать нельзя. Ожидание запроса не является барьером для всех MPI-процессов.

В этих Java bindings неблокирующие передачи используют прямые NIO-буферы, например `MPI.newIntBuffer(n)`. Они предоставляют память, с которой нативная MPI-библиотека может работать после возвращения Java-вызова. `put(i, value)` и `get(i)` обращаются к элементу по индексу; в наших программах эти операции не сдвигают текущую позицию буфера.

Полезный смысл асинхронности появляется, когда после запуска обмена можно выполнить независимые вычисления. В данной работе важнее другая возможность: сначала объявить все необходимые приёмы и отправки, а уже затем ждать. Так устраняется опасный порядок зависимостей.

### Почему возникает взаимная блокировка

Пусть процесс 0 сначала делает блокирующий `send` процессу 1, а процесс 1 одновременно делает блокирующий `send` процессу 0. Приёмы у обоих стоят следующими строками кода.

Если отправки требуют участия приёмников, получается цикл ожидания: процесс 0 ждёт приёма у процесса 1, процесс 1 ждёт приёма у процесса 0. До своих `recv` они не доходят. Маленькие сообщения могут скрыть ошибку за счёт внутренней буферизации, поэтому один успешный запуск такой схемы не доказывает её корректность для произвольного размера.

В исправленном варианте каждый процесс сначала запускает `iRecv`, затем `iSend`, и только после этого ждёт запросы. Оба приёма уже объявлены, поэтому ожидание не мешает партнёрам начать нужную операцию. Неблокирующий вызов с немедленным ожиданием перед объявлением остальных нужных операций мог бы сохранить прежнюю проблему; важен весь порядок вызовов.

### Группа и новый коммуникатор

`Group` описывает упорядоченный набор процессов. `getGroup()` получает группу существующего коммуникатора, а `incl(...)` выбирает из неё процессы в заданном порядке. Группа сама по себе не является каналом для `bcast` или `send`: для обмена создаётся коммуникатор.

Наш `COMM_WORLD.create(group)` — коллективный вызов на исходном коммуникаторе. Все процессы `COMM_WORLD` вызывают создание первого и второго коммуникаторов в одинаковом порядке, включая процессы, которые в новую группу не попадут. У исключённого процесса соответствующий результат проверяется через `isNull()`.

В группе `{3,4}` мировой ранг 3 получает локальный ранг 0, а мировой ранг 4 — локальный ранг 1. Поэтому корень `bcast(..., 0)` внутри этой группы — мировой процесс 3. Номер корня всегда относится к коммуникатору, на котором вызвана операция.

## 2 Как работает код и что рассказывать на защите

### Общая последовательность запуска

Каждый из пяти файлов — самостоятельная программа со своим `main`. Один Java-файл не вызывает `main` другого. Скрипт `./lab lab04` последовательно запускает отдельные MPI-программы: сначала проверку сообщений, затем ожидание, группы и обмены.

Внутри каждой программы сначала выполняется `MPI.Init`, затем ветвление по рангу, необходимые обмены и вывод. `MPI.Finalize()` находится в `finally`, чтобы завершение MPI выполнялось и при выходе через обычное Java-исключение. Все нужные неблокирующие запросы должны завершиться до `Finalize`; он не заменяет `waitFor`.

### TestProbe Проверка сообщения перед приёмом

Исходник: [TestProbe.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestProbe.java).

Процесс 0 создаёт `[10, 20, 30, 40, 50]` и циклом отправляет этот массив каждому рангу от 1 до `size-1`. Все отправки идут с тегом 1. На каждом другом процессе выполняется цепочка:

```text
main → probe(0, 1) → Status → getCount(MPI.INT)
     → создание int[count] → recv → печать массива
```

Размер массива выбирается по статусу найденного сообщения. Для приёма используются источник и тег из этого статуса. Это связывает проверку и последующий приём с теми же параметрами сообщения.

На защите покажи, что `probe` находится только в ветке получателей и не заменяет `recv`. Объясни вывод `source=0, tag=1, count=5`, а затем покажи пять значений в принятом массиве. Отдельный цикл ожидания вокруг блокирующего `probe` здесь не нужен.

### TestIProbe Отсутствие сообщения тоже является результатом

Исходник: [TestIProbe.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestIProbe.java).

До отправки каждый ненулевой процесс один раз вызывает `iProbe(0, 1)`. Затем все входят в `barrier()`. Процесс 0 начинает отправки только после этого барьера. Поэтому первая проверка получателей происходит до отправок и показывает `before_send_available=false`.

После барьера нулевой процесс рассылает массив, а получатели повторяют `iProbe`, пока не появится статус. `Thread.yield()` лишь предлагает планировщику уступить исполнение другому потоку; эта строка не принимает сообщение и не гарантирует определённую паузу. После получения статуса следуют выделение массива и настоящий `recv`.

На защите сравни две программы: у `TestProbe` ожидание находится внутри одного MPI-вызова, у `TestIProbe` программа сама решает, что делать после отрицательного результата. В текущем примере она продолжает опрос.

### TestWaitFor Ожидание двух разных запросов

Исходник: [TestWaitFor.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestWaitFor.java).

Требуется минимум два процесса. Каждый создаёт собственный прямой `IntBuffer` на одно число. Процесс 0 записывает 42, запускает `iSend` рангу 1 с тегом 99 и ждёт свой запрос. Процесс 1 запускает `iRecv` от ранга 0 с тем же тегом, ждёт свой запрос и только после ожидания читает число.

Это два локальных запроса: запрос отправителя и запрос получателя. Один объект `Request` между JVM не передаётся. Ранги выше 1 ничего не получают и печатают `role=idle`. При объяснении укажи, почему `completed=true` печатается после `waitFor`, а не сразу после `iRecv`.

### TestCreateIntracomm Два независимых состава участников

Исходник: [TestCreateIntracomm.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestCreateIntracomm.java).

После проверки `size >= 5` программа получает общую группу и создаёт группы A `{0,1,2}` и B `{3,4}`. Затем каждый мировой процесс выполняет оба `create`. Для каждого процесса выбирается его ненулевой новый коммуникатор; если он не вошёл никуда, обмен пропускается.

Мировые процессы 0 и 3 готовят массивы по формуле `rank*10+i`. В A корень рассылает `[0,1,2,3,4]`, в B — `[30,31,32,33,34]`. Участники каждой группы вызывают `selected.bcast(..., 0)` только на своём коммуникаторе.

| Мировой ранг | Группа | Локальный ранг |
| --- | --- | --- |
| 0, 1, 2 | A | 0, 1, 2 соответственно |
| 3, 4 | B | 0, 1 соответственно |
| 5 и выше | Ни одна | Внутригрупповой обмен не выполняется |

После работы освобождаются созданные коммуникаторы и объекты групп через `free()`. На защите главное — различить мировой и локальный ранг и объяснить, почему мировой ранг 3 становится корнем с номером 0.

### TestBlockingAndNonblocking Четыре режима обмена

Исходник: [TestBlockingAndNonblocking.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestBlockingAndNonblocking.java).

Программа требует ровно два процесса. `peer=1-rank` вычисляет партнёра. Ранг 0 формирует значения `i`, ранг 1 — `1000+i`, поэтому по содержимому можно определить, действительно ли пришёл чужой массив. `mode` и `n` задают режим и длину массива. Только для режима `nonblocking` дополнительно создаются прямые буферы.

Перед измерением стоит барьер, после него запускается локальный `System.nanoTime()`. Это измерение демонстрирует ожидание обмена в каждом процессе; оно не является исследованием ускорения параллельного алгоритма.

| Режим | Действия |
| --- | --- |
| `blocking` | Ранг 0 отправляет, ранг 1 принимает. Обмен односторонний. |
| `delayed` | Та же схема, но ранг 1 перед `recv` спит 300 мс. |
| `unsafe` | Оба ранга сначала выполняют `send`, затем `recv`. |
| `nonblocking` | Оба ранга запускают `iRecv`, затем `iSend`, ждут оба запроса и читают результат. |

В односторонних режимах тег равен 0. Во встречных режимах отправитель использует свой ранг как тег, а приёмник ожидает тег партнёра. Например, ранг 0 отправляет с тегом 0 и получает от ранга 1 с тегом 1.

`delayed` показывает, что короткий `send` может завершиться до задержанного приёма, а большой — ждать его. Массив из 262144 элементов `int` содержит 1048576 байтов, то есть 1 МиБ. По этим двум размерам нельзя установить точную границу внутреннего буфера MPI.

В `unsafe` перед опасной отправкой печатается `stage=before_send`, и `System.out.flush()` выталкивает эту строку в вывод. Если оба процесса дошли до неё и затем запуск прекращён по тайм-ауту, это наблюдение соответствует ожидаемой блокировке. Тайм-аут задаёт `mpirun`, он не исправляет алгоритм и не является частью MPI-протокола приложения.

В `nonblocking` сначала объявлены обе операции, а чтение `receiveBuffer` выполняется после обоих ожиданий. Затем код проверяет каждый элемент по ожидаемой формуле. Поля `first`, `last` и `checksum` удобны для показа, но внутренняя проверка сильнее одной контрольной суммы: она сравнивает весь массив.

### Последовательность рассказа и демонстрации

Начать можно так: «В этой работе я исследую управление обменом сообщениями. Сначала получаю сведения о сообщении без его приёма, затем показываю ожидание асинхронных запросов, создание отдельных групп участников и влияние порядка отправок и приёмов на корректность программы».

После этого последовательно открой пять файлов. У каждой программы назови участников, коммуникатор, тег, размер данных и условие, после которого их можно читать. Для групп покажи смену нумерации рангов; для встречного обмена проговори цикл ожидания и место его устранения.

Если спросят, почему успешный `send` не доказывает завершение приёма, ответь через право повторного использования отправляющего буфера. Если спросят, зачем `recv` после `probe`, объясни различие между метаданными сообщения и записью его содержимого в массив. Если спросят, почему неблокирующий обмен не зависает, покажи, что приёмы и отправки запущены до первого ожидания.
