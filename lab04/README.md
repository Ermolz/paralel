Запуск в Ubuntu / WSL из корня проекта:

```bash
cd ~/paralel
./lab lab04
./lab lab04 probe 2
./lab lab04 iprobe 4
./lab lab04 wait 2
./lab lab04 groups 5
./lab lab04 blocking 5
./lab lab04 delayed 262144
./lab lab04 nonblocking 262144
```

Для `probe`, `iprobe`, `wait`, `groups` число задаёт количество MPI-процессов.
Для четырёх режимов раздела 1.4 число задаёт длину массива; процессы всегда два.
`wait` требует минимум 2 процесса, `groups` — минимум 5. Остальные ранги в
`wait` не участвуют в передаче, а ранги выше 4 исключены из обеих групп.
`delayed` моделирует задержку перед `recv` паузой 300 мс.

Пример 1.3 раздела 1.4 запускается отдельно:

```bash
./lab lab04 unsafe 5
./lab lab04 unsafe 262144
```

У встречных блокирующих отправок возможна взаимная блокировка. Поэтому режим
`unsafe` ограничен пятью секундами и не включён в общий запуск. Его завершение
по тайм-ауту в опыте с большим массивом — наблюдаемый результат примера.
Вывод и код завершения сохраняются вместе с результатами исследования.

В книжных примерах исправлены неопределённый `myrank`, сигнатуры неблокирующих
методов и типы возвращаемых значений. `getGroup` возвращает `Group`, `create` —
`Intracomm`, исключённый коммуникатор проверяется через `isNull`. Для `iSend/iRecv`
используются прямые буферы. В `probe` убран лишний цикл ожидания: вызов уже блокирующий.

Для защиты: `probe/iProbe` только проверяют сообщение, приём выполняет `recv`.
`getCount` измеряет число элементов указанного MPI-типа. `iProbe` возвращает
`null`, если подходящего сообщения пока нет. `waitFor` вызывается у `Request`.
Все процессы исходного коммуникатора вызывают `create` в одинаковом порядке;
`bcast` выполняют только участники соответствующей новой группы.
Блокирующий `send` может завершиться за счёт внутренней буферизации — завершение
у получателя не гарантируется. В исправленном обмене приём и отправка запущены
до ожидания, а буферы читаются или изменяются только после завершения запросов.
Время запусков и порядок строк могут отличаться; это не тест производительности.
