## 1 Идея работы и коллективные операции MPI

### Зачем нужны коллективные вызовы

В MPI каждый процесс имеет отдельную память. Если один процесс подготовил массив, остальные сами его не увидят. Можно написать множество пар `send/recv`, но типовые схемы обмена удобнее выразить одним коллективным вызовом на каждом участнике.

Коллективная операция описывает общий результат взаимодействия группы. Например, `bcast` раздаёт одну копию исходных данных каждому участнику, а `gather` собирает разные фрагменты в один массив. MPI-реализация выбирает внутренний алгоритм: это может быть дерево передачи или другая схема. Наш код задаёт результат обмена и не реализует вручную все внутренние пересылки.

Все процессы коммуникатора должны вызвать соответствующую коллективную операцию с совместимыми параметрами. В частности, нельзя поместить `bcast` только внутрь `if (rank == root)`: тогда остальные участники не выполнят нужный вызов. Последовательность коллективных операций на одном коммуникаторе также должна согласовываться у всех участников.

В рассматриваемых программах коммуникатор один — `MPI.COMM_WORLD`. Ранг означает номер в этом коммуникаторе, а `size` — число MPI-процессов. Эти процессы не обязательно соответствуют отдельным физическим ядрам.

### Корень и локальное завершение

У `bcast`, `gather`, `gatherv`, `scatter` и `scatterv` есть `root`. Это ранг корневого процесса. В разных операциях его роль различается: при рассылке он является источником, при сборе — владельцем полного результата. Корень участвует в операции вместе с остальными: получает свою часть при `scatter` и добавляет собственный вклад при `gather`.

У операций с префиксом `all` выделенного корня нет. Например, `allGather` оставляет полный собранный массив на каждом процессе. Это не означает, что все участники обязательно имеют одинаковые входные данные; одинаковым является полученный полный результат.

Блокирующая коллективная операция гарантирует необходимое локальное завершение и возможность использовать соответствующие буферы после возврата. Она не должна трактоваться как универсальный барьер или гарантия одновременного выхода всех процессов. Порядок строк `println` в терминале также не задаёт порядок рангов.

### Как читать параметры буферов

`send` и `received` в исходниках — обычные локальные Java-массивы. MPI читает элементы отправляющего буфера и записывает элементы приёмного. Тип `MPI.INT` означает, что единицей данных является целое число.

Параметр `count` следует читать в контексте конкретной операции. В `gather` отправитель передаёт `count` элементов, а корень получает по `count` от каждого процесса. Поэтому полный результат занимает `count*size` элементов. Передать `count*size` вместо размера одного вклада было бы ошибкой.

Для `scatter` корень отправляет по `count` элементов каждому процессу, включая себя. Его исходный массив должен содержать все эти блоки, то есть `count*size` элементов. Для `allToAll` величина отправляемого блока также относится к одному адресату, а не ко всему исходному массиву.

### Что означают варианты с буквой v

Обычная операция предполагает одинаковый размер блоков. Вариант `v` задаёт размеры и размещение массивами `counts` и `displacements`. Элемент `counts[i]` относится к участнику с рангом `i`; `displacements[i]` задаёт начало его блока в соответствующем буфере.

Смещения в этих примерах измеряются в элементах `MPI.INT`, не в байтах. Смещение 5 означает позицию пятого элемента с нумерацией от нуля. Размеры должны согласовываться между отправителями и получателями, а приёмный массив должен вмещать все размещаемые данные.

В книжных примерах и нашей реализации длины блоков внутри вариантов `v` равны. Это допустимый частный случай. Гибкость интерфейса видна через явные массивы размеров и особенно через перестановку блоков с помощью смещений. Не следует приписывать программе разные длины, которых в текущих исходниках нет.

### Карта всех девяти операций

| Операция | Что происходит с данными | Где полный результат |
| --- | --- | --- |
| `bcast` | Один массив копируется всем участникам. | На всех. |
| `gather` | Равные вклады объединяются в порядке рангов. | На корне. |
| `gatherv` | Вклады размещаются по размерам и смещениям. | На корне. |
| `scatter` | Массив корня делится на равные блоки. | Каждый получает свой блок. |
| `scatterv` | Корень раздаёт блоки по размерам и смещениям. | Каждый получает свой блок. |
| `allGather` | Все вклады объединяются и доступны всем. | На всех. |
| `allGatherv` | То же с явными размерами и размещением. | На всех. |
| `allToAll` | Каждый отправляет свой отдельный блок каждому. | У каждого свой результат. |
| `allToAllv` | То же с размерами и смещениями для каждого партнёра. | У каждого свой результат. |

Коллективный сбор в этой лабораторной сохраняет отдельные значения. Арифметическое сложение вкладов здесь не выполняется. Даже если операция называется `gather`, она не суммирует массивы.

## 2 Как работает код и что рассказывать на защите

### Общая структура программ

Каждый файл имеет собственный `main` и запускается отдельно. Общая последовательность: `MPI.Init` → получение ранга и размера → заполнение входного массива → коллективный вызов → печать нужного результата → `MPI.Finalize` в `finally`. Между Java-файлами нет вызовов: скрипт `./lab lab05` последовательно запускает девять самостоятельных примеров.

Во многих примерах процесс `rank` заполняет массив по формуле `rank*10+i`. Это позволяет по числам увидеть происхождение данных: `[20,21,...]` пришёл от ранга 2. Формула используется для проверки размещения, а не для вычислительного ускорения.

### TestBcast Одна копия исходных данных каждому

Исходник: [TestBcast.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestBcast.java).

Каждый процесс создаёт массив из пяти элементов. Только ранг 0 заполняет его значениями `[0,1,2,3,4]`. Затем все процессы выполняют `bcast(data, data.length, MPI.INT, 0)`. В этом вызове у ранга 0 массив служит источником, у остальных — местом получения.

После вызова каждый печатает один и тот же массив. На защите покажи расположение `bcast` за пределами условной ветки заполнения. Именно поэтому в коллективной операции участвует весь коммуникатор.

### TestGather Равные вклады на последнем ранге

Исходник: [TestGather.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestGather.java).

Каждый ранг создаёт пять значений `rank*10+i`. Корень выбран как `size-1`; при четырёх процессах это ранг 3. Все вызывают `gather`, но полный массив печатает только корень. Его размер — `5*size`.

При четырёх участниках результат начинается так: `[0,1,2,3,4,10,11,12,13,14,...]`. Блок ранга 3 располагается последним, хотя именно этот процесс является корнем. Расположение определяется рангом отправителя, а не временем прихода или тем, кто выступает корнем.

`received` выделен во всех процессах для единообразия кода, но результат этого `gather` значим только у корня. Выделение массива у остальных не превращает операцию в `allGather`.

### TestGatherv Явное описание размещения

Исходник: [TestGatherv.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestGatherv.java).

Подготовка вкладов и выбор корня такие же, как в `TestGather`. Дополнительно цикл создаёт `counts[i]=5` и `displacements[i]=i*5`. При стандартном запуске на двух процессах это `{5,5}` и `{0,5}`.

Сначала в результат с позиции 0 попадают пять значений ранга 0, с позиции 5 — пять значений ранга 1. Получается `[0,1,2,3,4,10,11,12,13,14]` на ранге 1. Покажи на защите, какое место в обычном `gather` определялось автоматически, а теперь задано двумя массивами.

### TestScatter Раздача разных частей одного массива

Исходник: [TestScatter.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestScatter.java).

Здесь `count=3`. Процесс 0 создаёт и заполняет общий массив длиной `3*size`. При двух процессах это `[0,1,2,3,4,5]`. После `scatter` ранг 0 получает `[0,1,2]`, ранг 1 — `[3,4,5]`.

В отличие от `bcast`, участники получают разные участки исходного массива. В отличие от `gather`, поток данных направлен от одного полного массива к нескольким частям. У остальных процессов исходный `send` также выделен, но для этой операции содержимое отправляющего буфера значимо у корня.

### TestScatterv Блоки по указанным смещениям

Исходник: [TestScatterv.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestScatterv.java).

При четырёх процессах корень формирует 16 чисел от 0 до 15. Массив размеров равен `{4,4,4,4}`, смещения — `{0,4,8,12}`. Значит, ранг 1 получает четыре числа с позиции 4, то есть `[4,5,6,7]`; ранг 2 получает `[8,9,10,11]`.

Объясняй именно правило `send[displacements[r] ... displacements[r]+counts[r]-1]`. Оно даёт результат независимо от порядка строк терминала. Переставленные подписи рангов в книжном выводе не меняют смысл MPI-вызова; в нашем коде размещение согласовано с параметрами.

### TestAllGather Полный набор вкладов у всех

Исходник: [TestAllGather.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestAllGather.java).

Каждый из четырёх процессов готовит два числа: `[0,1]`, `[10,11]`, `[20,21]`, `[30,31]`. Все выделяют восемь мест и вызывают `allGather`. На каждом оказывается `[0,1,10,11,20,21,30,31]`.

Смысл можно объяснить как «собрать все вклады и сделать собранный набор доступным каждому». Это описание результата, а не утверждение, что библиотека обязательно сначала выполняет отдельный `gather`, затем отдельный `bcast`.

### TestAllGatherv Обратный порядок блоков

Исходник: [TestAllGatherv.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestAllGatherv.java).

Каждый процесс снова передаёт пять элементов. Отличие в формуле `displacements[i]=(size-1-i)*count`. При двух процессах ранг 0 размещается с позиции 5, ранг 1 — с позиции 0. Поэтому оба получают `[10,11,12,13,14,0,1,2,3,4]`.

Разворачивается порядок целых блоков, а не порядок элементов внутри блока. Это особенно наглядный пример того, зачем нужны смещения: итоговое размещение задаётся программой и не зависит от времени получения сообщения.

### TestAllToAll Каждый передаёт каждому своё значение

Исходник: [TestAllToAll.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestAllToAll.java).

Каждый процесс создаёт `size` чисел. При четырёх участниках у ранга 2 это `[20,21,22,23]`. Он отдаёт число 20 рангу 0, 21 рангу 1, 22 самому себе и 23 рангу 3. Размер блока на одного адресата равен 1.

Для ранга `r` полученный массив имеет вид `[r,10+r,20+r,30+r]`. Например, ранг 2 получает `[2,12,22,32]`. Каждый получатель видит значения в порядке отправителей 0, 1, 2, 3.

Если записать исходные массивы строками таблицы, `allToAll` в этом примере раздаёт её столбцы. Это помогает отличить операцию от `allGather`, где все получают одинаковую полную склейку строк.

### TestAllToAllv Обратное размещение отправителей

Исходник: [TestAllToAllv.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestAllToAllv.java).

Массивы `counts[i]=1` и `sendDisplacements[i]=i` сохраняют прежнее правило отправки. На приёме задаётся `receiveDisplacements[i]=size-1-i`. Поэтому значение от отправителя 0 записывается в последний элемент, а от отправителя 3 — в первый.

На ранге 2 результат будет `[32,22,12,2]`. У каждого процесса свои исходящие и входящие смещения. В общем случае количество, которое процесс `s` отправляет процессу `r`, должно согласовываться с количеством, которое `r` ожидает от `s`; одних достаточных размеров массивов для корректности недостаточно.

### Как провести рассказ по коду

Начать можно так: «Я исследую девять схем коллективного обмена. Для каждой задаю входные массивы так, чтобы числа показывали ранг источника. Затем по результату проверяю, кому достались данные и в каком порядке размещены блоки».

Показывай операции парами: `bcast` и `scatter`, затем `gather` и `allGather`, затем обычные варианты и варианты `v`. Заверши `allToAll`, потому что у него иная логика: каждый отправитель готовит разные данные для разных адресатов. В каждом файле сначала объясни размер буферов, затем параметры MPI-вызова и только потом вывод.

Команды из корня проекта:

```bash
cd ~/paralel
./lab lab05
./lab lab05 gather
./lab lab05 allgatherv
./lab lab05 alltoallv
```

Числа процессов для книжных примеров: `bcast`, `gather`, `scatterv`, `allGather`, `allToAll`, `allToAllv` — 4; `gatherv`, `scatter`, `allGatherv` — 2. Скрипт выбирает их автоматически. Фактический вывод сохранён в [results](results/) и в комментариях соответствующих Java-файлов.

Если спросят, зачем `v` при одинаковых длинах, покажи явное размещение и обратные смещения. Если спросят, почему `count=1` в `allToAll`, объясни, что это один элемент для каждого адресата. Если спросят о порядке вывода, раздели определённый порядок блоков в массиве и независимый порядок печати разных процессов.
