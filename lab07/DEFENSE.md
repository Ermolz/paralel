Работа охватывает разделы 3.1–3.3 [учебника](../MPI_Java_Mathpar_2025.pdf) из [задания](../Labs.pdf). В четырёх самостоятельных программах реализованы шесть процедур: `sendObject`, `recvObject`, `sendObjects`, `recvObjects`, `bcastObject` и `bcastObjectArray`. Общая идея — представить Java-объекты байтами, передать байты средствами MPI и восстановить объекты в другой JVM.

## 1 Идея работы и передача Java объектов

### Почему нельзя передать обычную ссылку

Каждый MPI-процесс работает в своей памяти. Java-ссылка на `Student` имеет смысл только в JVM, где этот объект создан. Другой процесс не может получить эту ссылку как число и по ней обратиться к исходному объекту. Даже на одном компьютере это разные адресные пространства и разные Java-кучи.

MPI хорошо передаёт массивы простых значений: `int`, `double`, `byte` и другие согласованные типы. Поэтому наш дополнительный слой преобразует сложную Java-структуру в `byte[]`. Для MPI содержимое этого массива — последовательность элементов `MPI.BYTE`; смысл полей студента или вложенного массива она не разбирает.

Получатель восстанавливает собственный объект с теми же переданными данными. Изменение полей или элементов у получателя не обновляет объект отправителя. Сериализация также не делает память распределённой программы общей.

### Сериализация и десериализация

Сериализация переводит состояние объекта и необходимое описание его структуры в последовательность байтов. В программе её выполняет `ObjectOutputStream`. `ByteArrayOutputStream` служит местом накопления байтов в памяти; файл на диске для этого не создаётся.

Получение происходит в обратном направлении: `ByteArrayInputStream` даёт поток чтения поверх принятого `byte[]`, а `ObjectInputStream.readObject()` восстанавливает Java-значение. Это десериализация. У принимающей JVM должны быть доступные совместимые классы, описывающие переданные объекты.

Наш `Student` — вложенный `record` с полями `surname`, `group`, `year`, реализующий `Serializable`. Этот интерфейс разрешает стандартную Java-сериализацию. В общем случае сериализуемыми должны быть и передаваемые объекты, достижимые через их нестатические сохраняемые поля. В примере поля состоят из строк и числа.

Массив `Object[]` содержит строки, автоматически упакованное целое `Integer` и вложенный `int[]`. Реальный тип каждого элемента сохраняется при сериализации. На выходе получается неоднородный массив: слово `Object` в объявлении не превращает все его элементы в строки.

### Какие действия выполняют Java и MPI

Путь данных для одного объекта выглядит так:

```text
Java объект отправителя
  → ObjectOutputStream
  → byte[]
  → MPI send или iSend
  → MPI recv
  → byte[] получателя
  → ObjectInputStream
  → Java объект получателя
```

`flush()` завершает передачу накопленных данных из `ObjectOutputStream` в его нижележащий поток до получения `toByteArray()`. Блоки `try-with-resources` закрывают потоки после использования. Исключения не заменяются молчаливым возвратом пустого объекта: методы объявляют `IOException`, `ClassNotFoundException` или `MPIException`, а вызывающий код получает ошибку.

Десериализация не выполняется самой MPI. Она начинается только после приёма массива, когда Java-код создаёт `ObjectInputStream`. Аналогично сериализация выполняется до запуска отправки; наличие `iSend` не делает этот подготовительный этап асинхронным.

### Размер байтового сообщения и число объектов

Размер сериализованного представления обычно не известен заранее. Он включает содержимое и служебные данные потока. Его нельзя вычислить как «число полей умножить на размер числа».

В обычном приёме используется `probe(source, tag)`. Из статуса берётся `getCount(MPI.BYTE)`, по нему выделяется `byte[]`, затем выполняется `recv`. `probe` лишь сообщает о подходящем сообщении; содержимое принимает следующий вызов.

У массива объектов нужно различать две величины: число байтов сообщения и число сериализованных объектов. `getCount(MPI.BYTE)` даёт первую. Для `recvObjects(count, source, tag)` вторая передаётся отдельным параметром. В наших программах обе стороны заранее знают, что элементов четыре.

### Как организована коллективная рассылка

Для `bcast` принимающие процессы должны иметь массив достаточной длины. Поэтому рассылка объекта выполняется двумя коллективными вызовами: сначала отправляется одно число — длина сериализованных данных, затем массив байтов указанной длины.

Все процессы вызывают оба `bcast` в одном порядке с одним корнем. Между ними получатели создают `new byte[length[0]]`. Никакая отдельная пара `send/recv` для передачи длины здесь не нужна.

У корня сохраняется исходный объект; другие процессы получают восстановленные локальные объекты. В `bcastObject` это отражено возвращаемым значением. В `bcastObjectArray` метод заполняет элементы заранее созданного массива получателя.

## 2 Как работает код и что рассказывать на защите

### Четыре независимые программы

У каждого файла собственный `main`. Общая схема запуска: `MPI.Init` → определение ранга → подготовка объекта на ранге 0 → вызов процедур передачи → печать → `MPI.Finalize` в `finally`. Стандартные демонстрации выполняются на четырёх процессах.

Похожие имена процедур находятся внутри соответствующих классов. Например, `TestBcastObject.main` вызывает свой `bcastObject`, а не `TestSendObject.sendObject`. Скрипт `./lab lab07` запускает четыре разные MPI-программы последовательно; он не вызывает их Java-методы из одной JVM.

### TestSendObject Передача одного студента

Исходник: [TestSendObject.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestSendObject.java).

На ранге 0 создаётся `Student("yermolovych", "GR03", 2026)`. Цикл по адресатам от 1 до `size-1` вызывает `sendObject(student, destination, 710)`. Внутри метода создаются потоки, объект сериализуется одним `writeObject`, получается `byte[]`, затем выполняется блокирующий `MPI.COMM_WORLD.send` с типом `MPI.BYTE`.

Каждый ненулевой ранг вызывает `recvObject(0, 710)`. Этот метод проходит четыре этапа: узнаёт статус через `probe`, выделяет массив нужного размера, принимает байты, читает один объект из потока и возвращает его.

```text
rank 0: main → sendObject → writeObject → send
rank > 0: main → recvObject → probe → recv → readObject → возврат в main
```

Число 710 — тег сообщений этого примера. Размер передаваемого сообщения определяется сериализацией, а не числом полей `Student`. Все получатели печатают одинаковые значения полей, хотя имеют собственные экземпляры объекта.

В этой реализации один и тот же студент сериализуется заново при каждом вызове `sendObject`. Это простая демонстрационная схема, а не оптимизация на минимальное число сериализаций.

### TestSendObjects Массив и неблокирующие отправки

Исходник: [TestSendObjects.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestSendObjects.java).

Ранг 0 готовит `{"yermolovych", "GR03", 2026, new int[]{10,20,30}}`. Внутри `sendObjects` цикл последовательно вызывает `writeObject` для каждого элемента одного и того же потока. Здесь не выполняется один `writeObject` для внешнего массива: записывается последовательность из четырёх объектов.

После сериализации создаётся прямой `ByteBuffer`. `buffer.put(data)` записывает байты и сдвигает позицию в конец. `buffer.flip()` переводит буфер к чтению: позиция становится 0, граница — числом записанных байтов. Затем `iSend` запускает передачу с тегом 720 и возвращает `Request`.

`main` хранит отдельный запрос для каждого получателя в `Request[]`. Сначала цикл инициирует все отправки, затем второй цикл вызывает `waitFor()` для каждого запроса. До завершения запросов содержимое передаваемых областей не должно изменяться. Ожидания стоят до выхода к `MPI.Finalize`.

Получатель вызывает `recvObjects(4, 0, 720)`. После `probe` и `recv` он создаёт `Object[4]`, открывает входной поток и четыре раза вызывает `readObject` в том же порядке, в котором отправитель записывал элементы. Если ожидать неправильное число объектов, контракт процедур нарушится: длина байтового массива сама не заменяет этот параметр.

Для печати применяется `Arrays.deepToString`, чтобы было видно содержимое вложенного `int[]`. Обычный `toString` массива не дал бы такого наглядного вывода элементов.

На защите проговори, что одновременно незавершёнными могут быть несколько MPI-отправок, но сериализация каждому адресату выполняется последовательно обычным Java-кодом. `iSend` позволяет не ждать окончание одной передачи перед запуском следующей; он не обещает автоматического ускорения всего примера.

### TestBcastObject Два bcast и возвращаемый объект

Исходник: [TestBcastObject.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestBcastObject.java).

`main` создаёт студента только на корне 0, а у остальных исходное значение `student` равно `null`. Затем каждый выполняет `student=bcastObject(student, root)`.

В методе корень сериализует студента и записывает длину в `int[1]`. Этот массив нужен как изменяемый буфер MPI: `bcast` заполняет его и у получателей. После первой рассылки они выделяют байтовые массивы, после второй получают их содержимое.

На ненулевых рангах метод возвращает результат `readObject()`, на корне — исходный `value`. Присваивание в `main` обязательно для логики этого интерфейса: Java передаёт параметры по значению, и локальная замена ссылки внутри метода сама по себе не переназначила бы переменную `student` вызывающей функции.

Покажи на защите оба `bcast`: первый относится к длине, второй — к содержимому. У коллективных вызовов здесь нет пользовательских тегов 710 или 720; согласование задают коммуникатор, корень и порядок коллективных операций.

### TestBcastObjectArray Заполнение элементов массива

Исходник: [TestBcastObjectArray.java](src/main/java/com/mathpar/NAUKMA/stud2026/GR03/yermolovych/TestBcastObjectArray.java).

Корень создаёт заполненный `Object[]`, остальные — пустой `new Object[count]` длиной 4. Все вызывают `bcastObjectArray(values, count, root)`. Корень записывает в поток `count` объектов; длина и байты рассылаются теми же двумя этапами.

Получатели читают объекты циклом и присваивают их существующим ячейкам `values[i]`. Поэтому метод возвращает `void`: менять саму ссылку вызывающей функции не требуется, изменяется содержимое доступного по ней локального массива. На корне его исходные элементы уже заполнены, и десериализация не выполняется.

В итоге все печатают `[yermolovych, GR03, 2026, [10, 20, 30]]`. Это подтверждает сохранение порядка, простых значений и содержимого вложенного массива.

### Как рассказать работу на защите

Начать можно так: «MPI работает с передаваемыми буферами, а Java-объект содержит структуру и ссылки. Я использую стандартную сериализацию, превращаю объект в массив байтов, передаю этот массив и восстанавливаю объект в другой JVM. Для неизвестной длины при обычном приёме использую `probe`, а для коллективной рассылки сначала рассылаю длину».

Затем открой `TestSendObject` и пройди полный путь одного студента. После этого в `TestSendObjects` покажи цикл записи объектов, прямой буфер и массив запросов. В двух коллективных программах сравни возвращаемый объект и изменение элементов массива. Во всех случаях укажи, что MPI передаёт байты, а Java-код задаёт их смысл.

Если спросят, почему используются два `bcast`, покажи необходимость выделить принимающий буфер до передачи его содержимого.
